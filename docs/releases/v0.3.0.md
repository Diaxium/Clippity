Clippity 0.3.0 adds **true HDR-preserving capture** for still images and video,
while keeping the existing HDR-to-SDR path as the compatibility default.

Still local-first: everything runs on your machine, no account, no cloud, and
the app sends no usage data anywhere.

This remains a **developer preview**. The binaries are unsigned and there is
still no auto-update path — see [Known gaps](#known-gaps).

## Downloads

| File | What it does |
| --- | --- |
| **`Clippity-0.3.0-Setup.exe`** | The full wizard — install, modify, repair, update, uninstall. One self-contained file with the app compiled into it. |
| **`Clippity-0.3.0-portable.zip`** | Unzip and run. No installer, no registry entries; settings stay beside the executable. |
| `SHA256SUMS.txt` | Checksums for both. |

Because the binaries are unsigned, SmartScreen will show *"Windows protected
your PC"* on first launch — **More info → Run anyway**. Verify the download
first if you'd rather:

```
certutil -hashfile Clippity-0.3.0-Setup.exe SHA256
```

**Requirements:** Windows 10 version 2004 (build 19041) or newer, and WebView2
(preinstalled on Windows 11).

## New

**HDR still images** — Preserve HDR captures the Windows compositor's linear
FP16 scRGB surface and saves a 16-bit BT.2020/PQ PNG. The file carries `cICP`,
mastering-display (`mDCV`), and content-light (`cLLI`) metadata, so highlight
headroom and wider color survive the capture instead of being flattened to SDR.

**HDR video** — MP4 recording can now keep the same FP16 desktop signal through
P010 conversion and HEVC Main10 encoding with BT.2020/PQ color metadata. This is
an opt-in setting and requires a Windows hardware encoder that accepts Main10.
Clippity checks the capture and encoder path before recording and reports an
explicit error if the selected display, region, driver, or encoder cannot
preserve HDR; it never silently substitutes an SDR recording.

## Improvements

**Compatibility remains the default** — ordinary screenshots and recordings
continue to use SDR PNG and H.264. On an HDR desktop, the existing high-precision
HDR-to-SDR tone map remains available for files and workflows that need broad
compatibility.

**Honest HDR constraints** — preserved HDR is limited to one display and simple
rectangular captures. Cursor compositing, Smart Enhance, freehand masks,
multi-area stitching, webcam/image recorder sources, and GIF are still 8-bit
operations and cannot be combined with Preserve HDR.

**Timed capture reliability** — countdown listeners are armed before commands
are invoked, and the tray/countdown window reasserts topmost state so the first
tick and the countdown UI are not lost to a fast backend response or focus
change.

**Dependency refresh** — the frontend and installer build stacks move to Vite
8 and the current React plugin; testing, type declarations, installer UI
libraries, Rust dependencies, and the benchmark harness are refreshed together.

## Internal

- A shared scRGB → BT.2020/PQ conversion now feeds both 16-bit PNG and P010.
- Persistent Desktop Duplication supports both BGRA8 and FP16 scRGB surfaces.
- HDR negotiation, capture loss, cross-display regions, and unsupported source
  composition fail explicitly instead of producing mislabeled or downgraded
  output.
- Media Foundation camera enumeration now owns and releases its returned COM
  activation array safely, and the JavaScript toolchain pins patched transitive
  dependency versions verified by `pnpm audit`.
- Decision record [0035](https://github.com/Diaxium/Clippity/blob/v0.3.0/docs/decisions/0035-hdr-preservation-is-an-explicit-output-path.md)
  documents the color contracts and compatibility boundaries.

## Upgrading

Run the new `Setup.exe` over an existing install, or unzip the portable build
beside the old one. Existing settings remain valid; Preserve HDR defaults off,
so established capture and recording workflows retain their current output.

## Known gaps

- **Binaries are unsigned.** SmartScreen will warn on first run.
- **No auto-update.** Updating means downloading a new build; the in-app
  updater is not wired up yet.
- **HDR video depends on hardware/driver support.** Windows' built-in software
  HEVC encoder does not guarantee Main10/P010 input. Preserve HDR video therefore
  needs a compatible hardware encoder exposed through Media Foundation.
- **HDR transforms are intentionally constrained.** Cursor, enhancement,
  irregular/stitched selections, and recorder source overlays remain SDR-only
  until those compositors operate in linear FP16.
- **No Content Security Policy** on the webview yet. The app loads no remote
  content and renders through React without raw HTML injection, but the policy
  itself is still to be added and is tracked as hardening work.
